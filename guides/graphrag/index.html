GraphRAG

GraphRAG answers structural questions that vector search handles poorly: “who reports to Bob?”, “what’s two hops from this project?”. In Core LLM Wiki it runs entirely on SQLite.

Vector / keyword read() Graph traverseGraph()
Starts from A query string A known anchor fact
Returns Loose top-K matches A connected subgraph (nodes and edges)
Good for “What do I know about X?” “What’s connected to X?”

End-to-end

Section titled “End-to-end”

  1. Turn on an ontology so the model emits edges

  2. Ingest or write as usual

    In strict mode the model returns typed facts with inline edges, and the engine resolves and stores them.

  3. Find an anchor and walk the graph

  4. Format it for the prompt

Traversal options

Section titled “Traversal options”
Option Default Notes
sourceId required The anchor fact ID
maxDepth — Clamped to the range 1–3
direction config.traversalDirection 'inbound', 'outbound', or 'both'
edgeTypes all [] matches nothing. Leave it out to match everything.
maxTraversalNodes config.maxTraversalNodes Cap on the number of nodes returned
minTraversalConfidence config.minTraversalConfidence Skip nodes below tentative, inferred, or certain
excludeSourceTypes config.excludeSourceTypes For example ['immutable_document']
excludeDrafts config.excludeDrafts Drafts are dead ends. The anchor is always returned.
asOf now Only walk edges whose two facts were both live at that time
tokenBudget — Keep nodes in breadth-first order until the budget runs out

Seed a graph without an LLM

Section titled “Seed a graph without an LLM”

Have structured data already (a code index, a CSV, an API response)? upsertGraph() writes nodes and edges directly, with the same (sourceRef, sourceHash) ownership as ingest:

  • It joins your transaction (you pass tx). It never begins or commits one itself.
  • Re-writing an identical (sourceRef, sourceHash) is a zero-count no-op.
  • The same hash under a different live sourceRef throws WikiSourceRefHashCollision.
  • A node ID owned by another entity throws WikiGraphNodeOwnershipConflict, and nothing is written. Entity-qualified IDs (repo:app/fn_processData) avoid accidental collisions.
  • Entry IDs share one namespace per database. An ID belongs to its entity as long as the row exists, including after a soft delete. The error deliberately doesn’t say who owns the ID.
  • An edge ID that already exists with a different entity, endpoints or type is caught later and throws a plain Error (the existing edge is never overwritten). Let it propagate so your transaction rolls back. Catching it and committing isn’t atomic.
  • ingestDocument applies the same ownership rule. It generates fresh IDs, so a collision there is unexpected. If one happens, ingestDocument’s own transaction rolls back. There’s no zero-write preflight check as with upsertGraph.
  • Authenticating callers and choosing the right entity ID is still your app’s job.
  • Embeddings aren’t computed here. They come from the next maintenance or reembed sweep.

Tip

Call syncSearchIndex() after the commit. Inside the transaction, the engine can’t yet see the rows you wrote.

How the query works

Section titled “How the query works”

traverseGraph() is a single recursive CTE. It walks edges in the requested direction, keeps a visited string to break cycles, filters by confidence and source type, and returns nodes ranked by MIN(depth) and then recency. After the CTE returns (node_id, depth) pairs, the engine loads the full facts and drops edges whose endpoints fell out.
