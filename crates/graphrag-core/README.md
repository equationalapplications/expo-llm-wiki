# graphrag-core

Portable native GraphRAG engine (vertical slice). Owns graph algorithms, graph
SQL, and typed results. No Tauri, windowing, Node, or React Native dependency.
The host owns connections, credentials, and lifecycle (REQ-OWN-01).

## Headless proof

```sh
cargo run -p graphrag-core --example proof
```

Builds an in-memory SQLite database, seeds a 3-node graph, runs a full
neighborhood traversal through `GraphRagEngine::traverse`, and prints the
result as TS-shaped JSON. Exits nonzero on any error. This is the
REQ-SLICE-03 proof artifact: a downstream host can run the engine without any
TS/JS.

## Public surface

- `GraphRagEngine::traverse` — **connection entry path** (REQ-SQL-01): the
  engine BEGINS a deferred snapshot read transaction, runs the whole pipeline
  inside it, and ENDS it before returning. On error the transaction is rolled
  back; none is ever left open on the host's connection.
- `GraphRagEngine::traverse_tx` — **transaction entry path** (REQ-SQL-01): the
  host owns the transaction; the engine never begins, commits, or rolls back.
  An engine error leaves the caller's transaction open and usable.
- Supporting modules: `error`, `types`, `validation`, `schema_check`, `okf`,
  `walk`, `edges`, `hydrate`.

Pipeline (both paths): validate schema → validate request → walk → induced
edges (chunk 500) → hydrate (chunk 500) → re-filter edges → assemble.

## Validation contract (REQ-INPUT-01)

`TraversalOptions` binds the exact TS input shape: camelCase JSON keys
(`maxDepth`, `direction`, `edgeTypes`, `maxTraversalNodes`,
`minTraversalConfidence`, `excludeSourceTypes`). Unknown keys are ignored;
snake_case keys are not recognized. Numeric options are clamped to their
documented bands; impossible requests surface as `UnsupportedLimit`, never a
silent reinterpretation.

## Schema contract (REQ-SQL-04)

`schema_check::validate_schema_conn` requires the `llm_wiki_entries`,
`llm_wiki_edges`, and `llm_wiki_meta` tables and the
`llm_wiki_meta.schema_version = 11` marker. Validation is read-only: the
engine never migrates or mutates the host schema. A wrong or missing version
is an error.

## Declared differences vs the TS baseline

Documented in module doc comments and pinned by fixtures in `tests/fixtures/`:

- **BFS in Rust instead of the recursive CTE** the baseline uses — the spec
  allows either implementation of the same traversal semantics.
- **Collision-free visited set** (HashSet of entry ids) instead of the
  baseline's array scan.
- **Unrounded real-valued depth** — depths stay `f64`; the baseline rounded
  through JS `Math` semantics.
- **Caller-supplied clock** — `now_ms` is a parameter on both entry paths;
  the baseline read the wall clock internally.
- **`embedding_blob` excluded from the projection** — the native `WikiFact`
  DTO does not carry it.
- **Deterministic induced-edge ordering** — edges are ordered deterministically
  rather than relying on SQLite row visitation order.

## Compatibility fixtures

`tests/fixtures/` JSON files are generated by
`packages/core/__tests__/traversalFixtures.generator.test.ts` from the real TS
baseline. Regenerate by running that vitest file; do **not** hand-edit them.

## Performance (REQ-PERF-01)

The benchmark harness scaffold lands with the CI task. Published numbers are
an adoption gate; none are claimed here.

## Host responsibilities

`rusqlite::Connection` and `Transaction` are `!Sync`: a host must not share one
across threads — keep each connection on its owning execution context and
serialize access host-side (REQ-SQL-01). The engine holds only `EngineConfig`
(trusted `table_prefix`, traversal defaults), which is `Clone` and freely
shareable.
